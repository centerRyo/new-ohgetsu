## Part 0 — 結論

**最推奨は 案D「生活管理指導表の電子化」、次点が 案A「給食アレルギー対応の連絡帳SaaS」。**

既存proposalの推奨だった**案1(食品表示スキャンアプリ)は、「時系列の蓄積で勝つ」という条件では推奨から外れる。** スキャンアプリが作るのは「JANコード→アレルゲン」という**静的な対応表**であり、これは時間が経っても価値が増えない。しかも同じ表はメーカー規格書・公開情報から資本のある競合が短期間で再構築できる。年月をかけた蓄積が参入障壁にならない。

代わりに推奨する2案は、いずれも「**相手が業務・制度上やらざるを得ないこと**」に入り込み、その副産物として時系列データが溜まる構造を持つ。

| | 案D 指導表電子化 | 案A 給食連絡帳 |
|---|---|---|
| 入り込む先 | 医師の年次記入業務 | 園と保護者の月次往復 |
| 対象疾患 | **5疾患すべて** | 食物アレルギーのみ |
| 溜まるデータ | 医師記入・最大12年分の年次記録 | 同一児童・最大6年分の日次記録 |
| 最初の顧客 | 個々のクリニック | 私立園 |
| 法務コスト | 高(医療情報) | 中 |

なお本レポート執筆時点で、この領域に**制度的な追い風が2つ**確認できた。いずれも既存3docsの調査時点(2026年前半)以降の動きである。

1. **2026年7月17日公布の改正個人情報保護法「統計特例」** — 統計作成目的に限り、要配慮個人情報を本人同意なしで事業者間提供できるルートが新設された(施行は公布から2年以内)。アレルギー症状データの二次利用にとって直接的な追い風。
2. **2026年4月1日施行の食品表示基準改正** — カシューナッツが義務表示(8→9品目)、ピスタチオが推奨表示に追加(19→20品目)。**経過措置が2028年3月31日まで**あり、この2年間は新旧表示が市場に混在する。つまり「表示が混乱している期間」が確定している。

## Part 1 — 既存4案をデータ資産の軸で再評価

「データが溜まるか」は、次の4つに分解して評価する。

| 評価項目 | 意味 |
|---|---|
| **蓄積の自動性** | ユーザー/事業者が自分の目的のために使う行為が、そのままデータ入力になるか |
| **時系列性** | 同じ対象を継続的に追跡でき、年月とともに価値が増すか |
| **代替困難性** | 後発が金・人海戦術で同じものを短期間に作れないか |
| **売れる形になるか** | API・データセットとして切り出せるか、買い手が想像できるか |

### 再評価の結果

| 案 | 蓄積の自動性 | 時系列性 | 代替困難性 | 売れる形 | データ軸の総合 |
|---|---|---|---|---|---|
| 案1 食品表示スキャン | △ スキャン時のみ | **✕ 静的な対応表** | **✕ 規格書から再現可能** | ○ API化しやすい | **低** |
| 案2 メニュー判定API | ✕ 入力=顧客の一時データ | ✕ 残らない | ✕ LLMラッパーは模倣容易 | ○ APIそのもの | **最低** |
| 案3 化粧品成分スキャン | △ | ✕ 静的 | ✕ INCI辞書は公開情報 | ○ | **低**(加えて薬機法リスク) |
| 案4 花粉症・症状ログ | ○ 日次入力 | **◎ 日次×年単位** | ○ ログは買えない | △ 買い手が曖昧 | **中** |

**この軸で見ると、既存proposalの評価順位はほぼ逆転する。**

### 案1が データ軸で弱い理由(重要)

既存proposalは案1を「将来 案2(B2B API)への横展開の土台になる」と評価した。これはデータ**量**の観点では正しいが、**資産の性質**を取り違えている。

- 作られるのは「JANコード → 含有アレルゲン」の**事実の対応表**。これは**誰が作っても同じ内容**になる。独自性がない。
- 一次情報(商品パッケージ表示)は全国のスーパーに物理的に置かれており、**競合も同じ情報源にアクセスできる**。参入障壁は「先に何SKU集めたか」だけで、資本を投じれば追いつける。
- 実際に日本には既に **[e食なび(eBASE)](https://www2.ebase-jp.com/eshoku_navi/)** が存在する。eBASEは**食品業界の商品情報プラットフォームを本業とする上場企業**で、メーカー側の商品情報を川上で押さえている。個人が店頭スキャンで下流から集めても、この構造には勝てない。
- さらに致命的なのは、**スキャンされた商品が「買った」のか「棚に戻した」のか区別がつかない**設計だと、行動データとしての価値も出ないこと。

> **結論:** 案1は「サービスとしての実現可能性」は高いが、「データ資産としての堀」はほぼ無い。B2Cサブスクで食えるならやる価値はあるが、**今回の目的(データでマネタイズ)には合致しない。**

### 案2が データ軸で最低な理由

判定APIは、顧客が投げてきたテキストを処理して返すだけで、**手元に何も残らない**。残しても他社の営業秘密(メニュー構成)なので二次利用できない。加えてLLMラッパーは技術的な模倣が容易。既存proposalが指摘した「B2B営業の重さ」に加え、**データ資産がゼロ**という問題がある。単体では不可。ただし後述するように、**他案のデータ資産を売る「出口」としては最適**。

### 案4が データ軸で再浮上する理由

花粉症の症状ログは、既存proposalでは「無料強豪とのレッドオーシャン」として高リスク判定だった。**サービスとしてのその評価は今も妥当**である。ただしデータ軸では、日次入力が自然に発生し同一人物を何年も追跡できる点で時系列性は4案中最高になる。ただし**買い手が曖昧**なのが弱点であり、かつ後述するように**花粉の実測データは既にウェザーニューズが押さえている**。

## Part 2 — データ軸で組み直した3案(A〜C)

「蓄積の自動性 × 時系列性 × 代替困難性」を満たすよう案を組み直す。

### 案A: 給食アレルギー対応の連絡帳SaaS「(仮)きゅうしょくノート」 ★次点推奨

**コンセプト**

学校・保育園と保護者の間で、食物アレルギー対応の献立確認を往復させる連絡帳。現状ほぼ**紙で運用されている**業務をデジタル化する。

```
毎月の流れ(現状: すべて紙)
  園・学校 → 翌月の献立表を配布
  保護者   → 自分の子のアレルゲンと突き合わせ、除去/代替の希望を紙に記入して返送
  園・学校 → 個別対応表を作成、調理場・担任に共有
  当日     → 誤配がないか複数人でチェック(サインリレー)
```

この往復をアプリ化する。園側は献立を登録、保護者は自分の子のアレルゲンを登録、**システムが自動で突き合わせて該当する日をハイライト**する。保護者は確認ボタンを押すだけ。当日のチェックリストもアプリ上で完結させる。

**なぜデータが溜まるのか(この案の核心)**

| 評価項目 | この案での状況 |
|---|---|
| 蓄積の自動性 | **◎ 業務そのものが入力**。園は毎月献立を必ず登録し、保護者は毎月必ず確認する。「データを入力してください」と頼む必要がない |
| 時系列性 | **◎ 同じ子どもを最大6年間追跡**できる。「小1で卵完全除去→小3で加熱卵可→小5で解除」という**耐性獲得の経過**が自然に記録される |
| 代替困難性 | **◎** 園という組織に入り込んだ後発は簡単に剥がせない(スイッチングコストが高い)。かつ過去の経過データは後から作れない |
| 売れる形 | ○ 後述 |

3つ目の「時系列」が決定的に重要である。**食物アレルギーの子どもの多くは成長とともに耐性を獲得する**が、その経過を数千人規模・年単位で追跡した民間データは日本に存在しない。これは病院のカルテにも断片的にしか残らない(受診時点のスナップショットのみ)。**日常の食事の場で毎日記録されるデータ**は、構造的にここにしかない。

**収益構造(B2C無料 + B2B有料)**

| 対象 | 課金 | 根拠 |
|---|---|---|
| 保護者 | **完全無料** | 課金すると導入時に園が保護者に説明する障壁になる。無料は導入の潤滑油 |
| 園・学校 | 月額3,000〜10,000円/施設 | 紙の印刷・配布・回収・照合の工数削減。誤配事故のリスク低減 |
| 給食受託会社 | 施設数に応じた法人契約 | 複数施設を一括管理できる価値 |
| (3年目以降)データ | 統計データ・API | 後述 |

**データの出口(3年目以降に見えてくるもの)**

現時点で買い手を確定させる必要はない。ただし蓄積後に成立しうる出口を、確度の高い順に挙げておく。

1. **アレルギー対応食品メーカーへの需要データ** — 「全国の園で、卵除去の子が最も多く代替を必要としているメニューは何か」は商品開発の直接の入力になる。加工食品メーカーのアレルギー対応商品開発は活発化しており([ダイヤモンド・チェーンストア](https://diamond-rm.net/sales-promotion/225826/))、需要の解像度を上げるデータには対価が発生しうる。
2. **自治体・研究機関向けの疫学データ** — 地域別のアレルゲン分布・耐性獲得率。改正個人情報保護法の統計特例が施行されれば、この提供ルートの法的整理が明確になる。
3. **API化(=案2の実質的な再生)** — 「献立テキスト → アレルゲン判定」APIを、**自社SaaSで検証済みの実データで裏打ちして**外販する。案2を単体でやると何も残らないが、案Aの後段としてやれば**精度という差別化要因**を持って売れる。
4. **保険商品との連携** — CAN EATが既にアレルギー事故補償保険を付帯している([CAN EAT アレルギーヒアリングシステム](https://biz.caneat.jp/allergyhearing/))。事故率の実データは保険設計の基礎資料になる。

**実現可能性と、正直な障壁**

- **技術的難易度: 低〜中。** 献立登録・アレルゲン突き合わせ・通知。個人開発で十分作れる。案1のような大規模DB構築が不要な点が大きい。
- **最大の障壁は営業。** 学校・保育園への販売は、決裁が遅く、自治体案件は入札が絡む。**個人開発者にとってここが最大の壁**であり、既存proposalが案2について指摘した問題がそのまま当てはまる。
- **競合は既に存在する。** [給食マイスター(日立産業制御ソリューションズ)](https://info.hitachi-ics.co.jp/product/kyusyoku/)、[食らぼキッズ](https://kids.shokulab.jp/service.php)、[らくらく献立8(夢工房)](https://www.yumekobo.jp/product/rakukon_hoiku.html) など、給食管理ソフトは複数ある。**ただしこれらは「調理場の業務システム」であり、保護者との往復を担っていない。** 狙うのはこの空白 — 施設内で閉じた管理ではなく、**保護者を含めた往復**である。この差が、そのまま「保護者側のデータも取れる」という差になる。
- **私立の単独園から始める。** 自治体の公立校は入札の壁が高い。決裁の速い私立幼稚園・認定こども園・小規模保育園を最初の顧客にする。

**最初の一歩**

コードを書く前に、**私立園の栄養士・園長5〜10人に「毎月のアレルギー対応の紙の往復に何時間かけているか」をヒアリング**する。既存の給食ソフトを入れている園でも、保護者との往復は紙のままか(=空白が実在するか)を確認するのが要点。

### 案B: 花粉症・症状の時系列ログ「(仮)症状カレンダー」 — 中リスク

**コンセプト**

既存proposalの案4をデータ軸で再設計したもの。花粉症・アトピー・喘息の症状を日次で記録し、**自分の悪化パターンを可視化**する。

**案4からの設計変更点**

既存proposalが「日本気象協会・ウェザーニュース等の無料強豪と競合するレッドオーシャン」と評価した点は正しい。したがって**予報では勝負しない。**

| | 既存の案4 | 案Bでの変更 |
|---|---|---|
| 主機能 | 花粉予報 + 症状ログ | **症状ログのみ**。予報は他社APIを表示するだけ |
| 訴求 | 「今日の飛散量が分かる」 | 「**去年の自分**と比べて今年はどうか」 |
| 差別化 | なし(予報は誰でも出せる) | **過去の自分のデータは他社が持っていない** |

「去年の自分と比較する」という機能は、**1年使い続けた人にしか価値が出ない**。これは新規ユーザーには弱いが、**継続ユーザーには競合が絶対に提供できない**価値になる。時系列で勝つという方針に最も忠実な設計。

**正直なリスク**

- **買い手が見えない。** 症状ログの買い手として想定される製薬企業は、既に自社で患者向けアプリを持っている(ヴィアトリスの[マイエピ](https://apps.apple.com/jp/app/id1493874335)等)。彼らは自前で集められるため、個人が集めたデータを買う動機が弱い。
- **プライバシー事故が一発で致命傷になる。** 経血記録アプリFloは2019年、ユーザーの健康データを本人同意なくFacebookに開示していたことが報じられ、FTCの調査・和解に至った。**健康データを集めるサービスは、データを売ろうとした瞬間に信頼を失うリスクを常に抱える。** 案Bはこのリスクが構造的に最も高い。
- ユーザー継続率が全て。日次入力を求めるアプリの継続率は一般に低い。
- 後述のとおり、**花粉の実測・症状収集はウェザーニューズが既に大規模に押さえている**。

### 案C: 飲食店向けアレルギー対応の記録SaaS — 非推奨(競合が先行)

外食店がアレルギー対応の確認・記録を行う業務SaaS。データとしては「どの店が実際に何に対応できたか」という**公開情報では埋まらない空白**が埋まる点が魅力。

**ただし、この領域は既に [CAN EAT](https://biz.caneat.jp/allergyhearing/) が先行している。** 同社はQRコードでゲストの食事制限情報を直接収集するシステムを、八芳園・雅叙園東京等のホテル・ウエディング会場に導入済みで、2024年8月にKIBOW社会投資ファンドから約5,000万円を調達している([PR TIMES](https://prtimes.jp/main/html/rd/p/000000062.000046724.html))。加えてアレルギー管理サービス(原材料ラベル撮影)も展開しており、**今回検討している構想のかなりの部分を既にカバーしている。**

資金調達済みの専業スタートアップが2年先行している領域に、副業・自己資金の個人が同じ形で入るのは不利。**非推奨とする。** ただし案Aの「学校・園」という領域は、CAN EATが主戦場としているホテル・ウエディング・飲食とは顧客セグメントが異なり、まだ空いている。

## Part 3 — 参入障壁の4類型と、消した領域

### 「参入しにくさ」は4種類ある

案Aの強さを分解すると、参入障壁には性質の異なる4つの型がある。**どの型の堀を掘るかで、事業の作り方がまったく変わる。**

| 堀の型 | 内容 | 後発が破れない理由 | 個人との相性 |
|---|---|---|---|
| **① 時間の堀** | 過去の記録が積み上がっている | **金で買えない**。3年前のデータは3年待つしかない | ◎ 副業・長期戦に最適 |
| **② 業務の堀** | 相手の日常業務に組み込まれている | 剥がすと業務が止まる。スイッチングコストが高い | ○ 営業が重い |
| **③ 制度の堀** | 法令・制度が定めた様式や義務に沿っている | 制度が変わらない限り需要が消えない。かつ**様式が全国共通**なので横展開しやすい | ◎ |
| **④ 関係の堀** | 専門家・団体との信頼関係 | 一朝一夕に作れない | △ 時間がかかる |

案Aは①②を持つ。**Part 4 の追加案は、特に③「制度の堀」を意識して探した。** 制度の堀は個人開発者にとって最も相性が良い。理由は、制度が「やらねばならない業務」を全国一律に作り出してくれるため、**営業で需要を説得する必要がない**からである。

### 調べた上で「消した」領域

提案の前に、**推奨しないと判断した**ものを挙げる。ここを潰しておかないと同じ検討を繰り返すことになる。

#### 花粉の実測データ — ウェザーニューズが既に押さえている

「気象データには飛散量しかなく、症状の実測がない」という空白を期待したが、**実在しなかった**。ウェザーニューズはIoT花粉観測機「ポールンロボ」を**全国1,000ヶ所**に設置し、1分ごとにデータを収集している。さらに**そのデータを気象データおよびユーザーからの症状報告と合わせて解析している**([ウェザーニューズ](https://jp.weathernews.com/news/45983))。

つまり「飛散実測 × 症状報告 × 気象」の3点セットを、数百万ユーザー規模で既に保有している。個人が後から同じ形で挑む領域ではない。**花粉症の「観測・予報・症状収集」ラインは全面的に非推奨。**

#### アトピーの症状記録アプリ単体 — 製薬企業の無料ツールと競合

マルホが患者向け無料アプリ「[アトピーノート](https://www.maruho.co.jp/information/2019052901.html)」を2019年から提供している。かゆみの程度・患部の写真・服用状況を記録できる。既存docsが指摘した「製薬企業の無料マーケティングツール型(Klarify等)とは競合できない」という構図が、日本のアトピー領域でも**そのまま成立している**。

記録アプリを単体でB2C提供するのは、無料かつ製薬資本のツールと殴り合うことになる。**単体では非推奨**(ただし案Eは、これを避ける形で設計している)。

#### 成人・職域のアレルギー — 痛みが分散していて突破口がない

職場の花粉症・喘息対策は、当事者の痛みが個人に閉じており、企業側に「支出してでも解決する」動機が生まれにくい。健康経営の文脈に乗せる手はあるが、それは**アレルギー事業ではなく健康経営SaaS事業**になり、巨大な既存プレイヤーの土俵。非推奨。

## Part 4 — 追加案(D〜F): アトピー・花粉症・喘息を含む探索

### 案D: 生活管理指導表の電子化「(仮)アレルギーカルテ」 ★最推奨

**制度の堀が最も強く、かつ4領域すべてを一度にカバーする唯一の案。**

#### 制度の説明 — なぜこれが特別なのか

**学校生活管理指導表(アレルギー疾患用)** は、アレルギー疾患のある児童・生徒が学校・保育所で特別な配慮を受けるために提出する、**全国共通様式の書類**である。

| 項目 | 内容 |
|---|---|
| 様式 | [日本学校保健会が定める全国共通様式](https://www.gakkohoken.jp/books/archives/232)(令和元年度改訂)。自治体が微修正して運用 |
| 対象疾患 | **食物アレルギー・アナフィラキシー / 気管支喘息 / アトピー性皮膚炎 / アレルギー性結膜炎 / アレルギー性鼻炎** |
| 記入者 | **医師**(保護者が医療機関に持ち込んで記入を依頼する) |
| 提出頻度 | **原則として毎年更新**。アレルギー疾患は成長に伴い症状が変化するため |
| 制度上の位置づけ | 2022年4月より、診断書(自費文書)から**保険適用の診療情報提供書**に変更された |

この書類の性質を、堀の観点から見ると異常なほど条件が揃っている。

| 堀の型 | この案での状況 |
|---|---|
| **③ 制度の堀** | **◎◎** 法令・ガイドラインが定めた様式。全国共通なので1つ作れば全国で使える。制度が続く限り需要が消えない |
| **① 時間の堀** | **◎◎** 毎年更新される = **1人の子どもについて最大12年分の年次スナップショット**が溜まる。しかも**医師が記入した信頼性の高いデータ** |
| **② 業務の堀** | ○ 医師・園・保護者の3者の業務に入る |
| **④ 関係の堀** | ○ 医師会・学校保健会との関係が効いてくる |

**「毎年・医師が・全国共通様式で・5疾患すべてについて」記入する**データは、日本のアレルギー領域で他に存在しない。これが案Dを最推奨とする理由である。

#### 現状の何が壊れているか

現在この書類は、ほぼ完全に紙で運用されている。

```
毎年春の流れ(すべて紙)
  保護者 → 学校から用紙をもらう
  保護者 → 医療機関を受診し、用紙を渡す
  医師   → 手書きで記入(前年の内容は手元にない。ゼロから書く)
  保護者 → 受け取って学校に提出
  学校   → 保健室・担任・給食調理場で内容を共有(コピーを配る)
```

ここには3者すべてに痛みがある。

- **医師**: 毎年春に大量の指導表記入が集中する。**前年に自分が何と書いたかを見返せない**ため、毎回カルテを遡る。
- **保護者**: 毎年病院に行き、用紙を渡し、受け取り、学校に出すという往復。
- **学校**: 紙を集約し、内容を関係者に配る。誰の分が未提出かの管理も紙。

#### サービス設計

**3者をつなぐが、最初は1者だけに絞って作る。**

```
Phase 1(まずここだけ): 医師の記入支援
  ├ Webで指導表を入力 → 全国共通様式のPDFを出力して印刷・押印
  ├ 患者ごとに前年の記入内容を保存し、翌年はそれを呼び出して差分だけ修正
  └ 「去年と同じ内容でよければ1クリック」が最大の価値

Phase 2: 保護者への電子共有
  └ 発行された指導表を保護者がスマホで受け取り、学校に提出

Phase 3: 学校側の受け取り・管理画面
  └ 未提出者の一覧、疾患別の集計、関係者への共有
```

**Phase 1を医師から始めるのが要点。** 学校や保護者から始めると導入の意思決定が遅く、かつ全国に散らばっていて営業が効かない。一方、医師は**個々のクリニックが独立して意思決定でき**、かつ「毎年春の記入地獄」という明確な痛みを持っている。小児科・アレルギー科の1院に入れてもらうことから始められる。

そして重要なのは、**Phase 1だけで既に時間の堀が掘れている**ことである。医師が前年分を呼び出すために使い続ける限り、年次データは自動的に積み上がる。

#### 収益構造

| 対象 | 課金 | 根拠 |
|---|---|---|
| 医師・クリニック | 月額3,000〜8,000円/院 | 記入工数の削減。春の繁忙期の負荷軽減 |
| 保護者 | 無料 | 導入の潤滑油 |
| 学校・園 | 月額(Phase 3以降) | 未提出管理・共有の効率化 |
| 自治体 | 教育委員会単位の契約(将来) | 域内の集計・把握 |

#### データの出口

指導表データは、日本のアレルギー領域で**最も研究価値の高い民間データセット**になりうる。

1. **疫学データ** — 地域別・年齢別の5疾患の有病率と**経年変化**。「どの地域でアトピーの子が増えているか」を年次で追える民間データは現状存在しない。
2. **耐性獲得の追跡** — 食物アレルギーの除去品目が学年とともにどう減るか。医師記入なので信頼性が高い。
3. **製薬企業の疫学マーケティング** — 喘息・アトピーの重症度分布は治療薬の市場規模推定に直結する。既存docsが示すとおり喘息バイオ市場はCAGR 12%超で伸びており、患者分布データの需要は構造的にある。
4. **自治体の政策データ** — アレルギー対策の計画立案の基礎資料。

2026年7月17日公布の改正個人情報保護法の**統計特例**(統計作成目的に限り要配慮個人情報の事業者間提供が同意なしで可能、施行は公布から2年以内)は、この出口に直接効く。

#### 障壁とリスク(正直に)

- **医師への営業。** 案Aの園への営業と同程度に重い。ただし小児科・アレルギー科は専門学会・研究会のコミュニティが濃く、**1人の理解ある医師が他の医師を紹介する**連鎖が起きやすい点は有利。
- **既に支援ツールが存在する。** 学校生活管理指導表の作成支援アプリが既にある旨の記述を確認した([学校保健ポータルサイト](https://www.gakkohoken.jp/books/archives/232)周辺)。**これが何者で、どこまでカバーしているかの実地確認が最優先事項。** ただし公的機関の無料ツールは通常「様式を埋めてPDFを出す」だけで、**年次の蓄積・呼び出しまでは持たない**ことが多い。差別化点はそこ。
- **医療情報の取り扱い。** 医師が記入する診療情報を預かるため、3省2ガイドライン(医療情報システムの安全管理)への準拠が必要になりうる。**個人開発で最も費用がかかるのはここ**で、クラウド構成と規約の設計を最初から専門家に相談すべき。
- **押印・紙提出の慣行。** 学校が紙・押印を要求する間は完全電子化できない。だからPhase 1を「**PDF出力して印刷する**」設計にしてある。紙の運用を否定せず、**その手前の作成工程だけを取る**のが現実解。

### 案E: 経口免疫療法・負荷試験後の自宅摂取記録「(仮)ちょっとずつノート」

#### 着眼点 — 制度の隙間に落ちている記録

食物経口負荷試験は、病院で少量を摂取して問題なければ、**自宅で同じ量を継続して食べてもらう**という流れを取る。目的は「安全摂取可能量の決定」と「**耐性獲得の診断**」である。

この**自宅での継続摂取記録が、現在ほぼ完全に保護者任せ**になっている。ノート、スマホのメモ、母子手帳の余白。そして次の受診時に口頭で医師に伝える。

- 記録が残らないため、医師は**保護者の記憶に頼って**次のステップを判断する
- 症状が出たときの状況(体調、運動、量)が記録されていないと、**何が誘因だったか分からない**
- 数年かけて少しずつ量を増やす治療なのに、**その全経過を通して見られる記録がない**

#### なぜ後発が参入しにくいか

| 堀の型 | 状況 |
|---|---|
| **① 時間の堀** | **◎◎** 治療自体が数年単位。「卵1/8個から始めて3年で全卵1個」という**経過そのもの**が記録される。これは最も濃い時系列 |
| **④ 関係の堀** | ◎ 医師が患者に勧めるツールになれば、その医師との関係が堀になる |
| ② 業務の堀 | △ 保護者の自主的な記録に依存 |
| ③ 制度の堀 | △ 制度上の義務ではない |

#### 設計上の要点

**製薬企業の無料アプリと同じ土俵に立たないこと。** アトピーノートやマイエピのような「症状を記録する汎用アプリ」を作ると、資本で負ける。

差別化は**「負荷試験後の段階的摂取」という極めて限定された文脈に特化する**こと。

```
汎用の症状記録アプリ         案Eの設計
  「今日の症状を記録」    →   「今日は卵 1/4個 を食べた / 症状なし」
  自由入力の日記          →   医師が設定した摂取ステップに沿った記録
  記録して終わり          →   次の受診時に経過グラフを医師に見せる
```

医師が「次の受診まで、このアプリで記録してきてください」と**処方するように渡せる**設計にする。汎用アプリではなく、**治療プロトコルの一部**として位置づける。

#### 収益構造とリスク

- 保護者: 無料 / 医療機関: 月額(医師用の閲覧ダッシュボード。複数患者の経過を一覧できる)
- データ: 耐性獲得の経過データ。**アレルギー対応食品メーカーにとって「どの段階の子が何を食べたいか」は商品開発の直接の入力**になる
- **医療行為との線引きが案Dより微妙。** 「食べてよい量」をアプリが示唆すると医療行為に近づく。**あくまで医師の指示を記録するだけ**という設計を厳守し、アプリが判断を示さないこと。アナフィラキシーのリスクがある領域なので、免責設計は案Aより厳格に。
- ユーザー数が案Dより少ない。負荷試験を受けている児は食物アレルギー児の一部。
- 保護者の入力継続に依存する(業務の堀がない)。

### 案F: 喘息の発作・吸入記録 × 学校連携 — 案Dのサブセット

喘息は、指導表の対象疾患であり、かつ**学校での発作対応**という具体的な業務がある。体育の授業、運動会、宿泊行事のたびに「この子は大丈夫か」の確認が発生する。

- **時間の堀**: ○ 発作の季節性・年次変化
- **制度の堀**: ○ 指導表の対象疾患
- **参照モデル**: 米Propeller Healthが吸入器センサー+アプリで**ResMedに2.25億ドルで買収**された(既存docs参照)。ただし**ハードウェア前提**であり、個人には再現不能

ソフトのみで作るなら案Dの一機能として実装するのが自然で、**単体の事業にする必然性が薄い**。案Dのサブセットと位置づける。

### 推奨 — 案D、ただし案Aとの選択は「営業できる相手」で決める

**データ資産としての強さでは、案Dが案Aを上回る。** 理由は3点。

1. **毎年・医師記入・全国共通様式**という3条件が揃ったデータは他に存在しない。データの信頼性が段違い。
2. **5疾患すべてをカバー**する。食物アレルギーに閉じず、アトピー・喘息・鼻炎まで一度に射程に入る。
3. **制度の堀**があるため、需要を営業で説得する必要がない。「毎年やらねばならない作業」が既にそこにある。

一方で、案Dは**医療情報を扱うため法務・セキュリティの初期コストが案Aより明確に高い**。自己資金数百万円のうち相当部分がここに消える可能性がある。

#### 選択の分かれ目

実際にどちらを選ぶかは、**どちらの相手に話を聞きに行けるか**で決めるべきである。

| もし… | 選ぶべき案 |
|---|---|
| 知人・紹介で**小児科/アレルギー科の医師**に会えるなら | **案D** |
| 知人・紹介で**私立園の園長・栄養士**に会えるなら | **案A** |
| どちらにも会えるなら | **案D**(データ資産が上位互換のため) |

個人開発者にとって最初の顧客は「たまたま話を聞いてくれた1人」から始まる。**机上の優劣より、実際に扉が開く方を取るべき**である。

#### 着手前に必ず確認すべきこと(案Dの場合)

1. **既存の指導表作成支援ツールが何者か。** 日本学校保健会周辺に支援アプリが存在する。それが無料の公的ツールなのか、どこまでカバーしているのか、**年次の蓄積・呼び出し機能を持つか**を実地で確認する。ここが埋まっていたら案Dは成立しない。
2. **医師5〜10人へのヒアリング。** 「毎年春の指導表記入にどれだけ時間を取られているか」「前年の記入内容をどう参照しているか」を聞く。**前年分を見返せないことが痛みとして実在するか**が核心の仮説。
3. **医療情報の取り扱い要件の見積もり。** 3省2ガイドライン準拠が必要かを専門家に確認し、初期費用を把握してから着手を判断する。

## Part 6 — 推奨案の3年計画とデータ設計

副業・長期戦(2〜3年)という前提に合わせ、段階を切る。以下は案Aを例に記すが、**段階の考え方は案Dにもそのまま適用できる**(「園」を「クリニック」に読み替える)。

### Year 1: 1者に無料で入れて、業務を完全に理解する

- 私立園1〜3施設(案Dならクリニック1〜3院)に**無償で導入**し、業務を回す。この段階の目的は売上ではなく、**「紙で何が起きているか」を完全に理解すること**。
- この期間に作る機能は最小限に絞る。
- **データ設計だけは最初から本気でやる**(後述)。ここを後から直すのは不可能に近い。
- 判断基準: 3ヶ月運用して、相手が「紙に戻りたい」と言わないか。

### Year 2: 有料化と、10〜30施設への横展開

- 月額課金を開始。Year 1の相手に「いくらなら払うか」を率直に聞く。
- 横展開は**同一法人の系列 → その法人が繋がっている先**という紹介の連鎖で進める。個人開発者に飛び込み営業の時間はない。
- この時点で数百〜数千人分の**1年以上の継続データ**が溜まる。

### Year 3: データを商品にする

- ここで初めて、Part 2・Part 4 で挙げた出口(需要データ / 疫学データ / API / 保険)のどれが現実的かを、**実際に溜まったデータを見て**判断する。
- 判定APIの外販(案2の再生)を検討するならこの段階。自社SaaSの実データで精度を検証済みという裏付けを持って売る。

### データ設計上、Year 1から必ず守ること

要配慮個人情報を扱う覚悟を前提に、最初から組み込むべき設計を挙げる。**後から足せない項目ばかり**である。

| 項目 | 内容 |
|---|---|
| **同意の分離** | 「サービス利用のための同意」と「統計利用のための同意」を**別々に**取る。後者は拒否してもサービスが使えること |
| **履歴を上書きしない** | アレルゲン設定を変更したとき、**古い値を上書きせず履歴として残す**。これが耐性獲得の経過データそのものになる。上書き設計にすると時系列資産がゼロになる |
| **イベントログ** | 「いつ・誰が・何を変更/確認したか」を追記型で全て残す |
| **識別子の分離** | 児童の氏名等の直接識別子を、症状・アレルゲンデータと別テーブルに置き、統計利用時に切り離せる構造にする |
| **利用規約の明記** | 統計目的での二次利用の可能性を、**曖昧な包括同意ではなく具体的に**書く。Floの事例が示すとおり、ここを曖昧にすると後で致命傷になる |
| **相手方との契約** | 園・クリニックが持つ児童データの取扱いについて、受託か共同利用かを契約書で明確にする。ここは**弁護士レビューの費用を見込む**(自己資金の範囲で優先的に配分すべき支出) |

改正個人情報保護法の統計特例(2026年7月17日公布、施行は公布から2年以内)により、統計作成目的に限れば要配慮個人情報の事業者間提供が同意なしで可能になる見込みだが、**施行前の現時点では従来どおり本人同意が必要**である。また特例は「特定個人のプロファイリング」「ターゲティング広告への利用」を明確に禁じているため、**個人単位で売る出口は最初から想定しない**方がよい。

### 補足 — 食品表示基準改正という2年間の窓

2026年4月1日施行の食品表示基準改正で、カシューナッツが義務表示に追加され特定原材料は9品目に、ピスタチオが推奨表示に追加され20品目になった。**経過措置は2028年3月31日まで**で、この2年間は旧表示(カシューナッツ未記載)と新表示が市場に混在する。

これは案1(スキャンアプリ)にとっては「旧表示の商品を新基準で判定してしまう」というリスク要因だが、**案A・案Dにとっては営業の入口になる**。園・学校の栄養士や医師は2028年までに献立・規格書・指導表の見直しを迫られており、「その確認作業を楽にする」という文脈でアプローチできる。制度変更は、平時なら会ってもらえない相手に会う理由になる。
